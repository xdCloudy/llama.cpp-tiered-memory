# Baseline builds and first CPU throughput capture

## Scope
Initial CPU builds were completed from upstream SHA `bd4eeaa047006cb1fe71999fbd11134b5836e167`, before any runtime source changes. The exact same runtime source is both the upstream and feature-disabled fork control at this stage. No inference feature is implemented, so there is no feature-enabled result yet.

## Host and tools
- Date: 2026-10-07.
- Windows: Windows 11 Pro build 26200, 63.7 GiB physical RAM, Intel Core i5-14600K (14 cores / 20 logical processors), MSVC 19.44.35228.0, Visual Studio 2022 Build Tools, CMake 4.4.4, Ninja 1.13.2.
- GPU: NVIDIA GeForce RTX 3060, 12,288 MiB, driver 610.74; CUDA Toolkit 13.3.73.
- Linux environment: WSL2 Ubuntu 24.04, kernel `6.18.33.2-microsoft-standard-WSL2`, GCC/G++ 13.3.0, CMake 4.4.4, Ninja 1.13.2. WSL reported 15 GiB total memory, so it is not a bare-metal memory baseline.
- CMake options: `GGML_CUDA=OFF`, `LLAMA_BUILD_TESTS=OFF`, `LLAMA_BUILD_EXAMPLES=ON`; Release configuration. Windows used Visual Studio 17 2022, x64. Linux used Ninja.

## Build results
- Windows CPU `llama-cli`: PASS at `build-win-vs-cpu/bin/Release/llama-cli.exe`.
- WSL Ubuntu CPU `llama-cli`: PASS at `build-wsl-cpu/bin/llama-cli`.
- Windows CUDA `llama-cli` and `llama-bench` builds: PASS with CUDA Toolkit 13.3.73, MSVC 19.44, and architecture 86-real for the RTX 3060.
- An initial Windows Ninja attempt selected Clang without the Windows SDK and failed to link system libraries. Switching to the installed Visual Studio generator resolved the toolchain issue.
- The Windows build logged a failed attempt to download the optional UI asset archive, then embedded 70 available assets and completed the CLI build.
- Linux configuration initially lacked CMake/Ninja and `sudo` access. User-scoped wheels in `/tmp/llama-build-tools` supplied the build tools; no system packages were changed.

## First inference throughput run
The model was already present on the host and was used read-only: Qwen3.5-0.8B BF16, 772,845,888 parameters, GGUF file size 1,546,700,032 bytes. It is outside this repository and is not redistributed here.

Command settings: Windows Release CPU build; prompt 256 tokens; generation 64 tokens; batch/ubatch 512; GPU layers 0; threads 14; flash attention off; mmap load; K/V cache F16; repack on; 3 repetitions; llama-bench JSON output.

| Path | Mean tokens/s | Standard deviation | Samples |
|---|---:|---:|---|
| Prompt processing (256 tokens) | 237.97 | 19.70 | 253.50, 244.60, 215.80 |
| Generation (64 tokens) | 15.35 | 2.66 | 13.45, 14.21, 18.39 |

Raw output: [win-cpu-qwen35-08b.json](raw/2026-10-07-win-cpu-qwen35-08b.json).

The same workload with all layers on CUDA (`-ngl 99`) measured 6,732.78 prompt tokens/s (standard deviation 632.98) and 146.69 generation tokens/s (standard deviation 1.84). Raw output: [win-cuda-qwen35-08b.json](raw/2026-10-07-win-cuda-qwen35-08b.json). This model fits entirely in the 12 GiB GPU; it is not a partial-offload or capacity test.

## Limits
This is one small-model workload with three repetitions. CPU results show noticeable variance; CUDA token generation is more stable. These measurements do not establish memory savings, startup/load time, peak RAM/VRAM, PCIe traffic, a Linux throughput result, or a packed-memory benefit. The local model is not representative of a model larger than VRAM. Add memory telemetry, more runs, bare-metal Linux, and a model that exercises partial offload before drawing cross-platform or capacity conclusions.
